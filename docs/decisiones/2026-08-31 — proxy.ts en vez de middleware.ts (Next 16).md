# `proxy.ts` en vez de `middleware.ts`

## Contexto

Escribí primero `middleware.ts` para centralizar CORS, siguiendo la
convención que conocía. Al levantar el servidor por primera vez, Next.js
16.3.4 avisó: la convención `middleware` está deprecada y renombrada a
`proxy` desde la v16.0.0 — sigue funcionando, pero con warning.

## Decisión

Renombré el archivo a `proxy.ts` y la función exportada de `middleware` a
`proxy`, siguiendo la guía oficial de migración
(`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`).
El `config.matcher` no cambió.

## Por qué no me quedé con `middleware.ts`

El propio scaffold de `create-next-app` (`AGENTS.md`) advierte
explícitamente que Next 16 tiene cambios que no coinciden con lo que un
modelo entrenado antes de esa versión asume, y pide leer la documentación
empaquetada antes de escribir código nuevo. Usar una convención marcada
como deprecada desde el día uno no tiene sentido en un proyecto que existe,
justamente, para tener buena base a futuro.

## Consecuencias

Ninguna funcional — el comportamiento de CORS es idéntico. Si en algún
momento reviso otro código Next.js más viejo (ej. ejemplos, tutoriales)
que use `middleware.ts`, tengo que acordarme de que en este proyecto
corresponde `proxy.ts`.
